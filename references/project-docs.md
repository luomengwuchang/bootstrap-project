# 项目文档约定与审阅

在填写、改进或检查 `PLANS.md`、`PROJECT_CONTEXT.md`、`README.md` 时阅读本页。纯脚本预览和独立 HTML 报告不需要这份流程。

## 内容归属

| 文档 | 维护内容 | 更新时机与长度控制 |
| --- | --- | --- |
| `PLANS.md` | 当前任务、范围与验收、执行状态、验证依据、下一步、历史入口 | 任务发生实质变化或交接时更新；只保留近期闭环记录，历史和长细节通过链接读取 |
| `PROJECT_CONTEXT.md` | 已核实的定位、技术栈、实际结构、开发与测试要求、长期决定 | 稳定事实变化时修订相应段落；长设计说明放专项文档，只保留理解项目所需的结论和链接 |
| `README.md` | 对外简介、环境前提、安装与启动、文档导航 | 功能入口、环境或运行方式变化时更新；保留最短可用路径，操作细节通过链接展开 |

通用安装与启动命令在 README 维护一份，上下文文档链接过去；项目专有的开发、测试和构建要求放在上下文文档。已有项目若明确采用其他分工，保留可用的主来源并链接，避免为了套模板制造第二份说明。

翻译标题或移动文档时，同步修订相对路径和锚点链接；例如 README 的“运行方式”改名后，上下文中的对应链接也要更新。

先按仓库既有指令入口读取约定，再读上下文和当前计划；运行项目时查 README，追溯任务时才读相应历史。生成这三份文件不会让客户端自动加载它们，也不会自动修改 `AGENTS.md`。

## 填写与维护计划

- 按用户请求和现有代码确定哪些是事实、哪些是拟议工作。模板日期、脚本退出成功或文件存在，都不能代替内容核实；初始化结果只能根据实际创建、跳过、失败及验证情况记录。
- 多步骤、跨会话、需要交接的工作使用正式条目；简单的一次性修改不强制建计划。新建和翻译时保留编号、范围、验收、状态、结果与下一步的含义，不要求已有项目机械改用相同标题或字段排版。
- 同一任务的纠正更新原条目，保留仍适用的目标和约束。切换焦点时把未结束任务及恢复信息留在当前计划；只有明确完成或取消才转入历史，并补上结束日期。会话结束不自动暂停、取消或完成任务。
- `受阻` 说明缺少的必要条件及解除方式；`已暂停` 只表示用户明确要求暂缓。记录局部阻塞时继续可以独立推进的已授权工作，待办池不是额外执行授权。
- 验收条件应能观察，验证与改动风险相称：文案可以核对渲染和差异，行为改动使用相关测试或实际操作。记录方法、结果、证据路径及未验证项；适用验收条件仍未满足时，不能把“实现已写完”作为完成依据。
- 待办池保留尚未纳入当前计划的候选项及来源或触发条件，合并重复项；纳入计划后移除重复项，完成或取消的结果留在对应记录中。不要在每一轮对话后追加流水账。

## 归档顺序

1. 只从已结束记录中选取归档对象，按结束日期保留最近 5 条；体积超限时可再减少主文件中的历史条数。不能为满足数量或大小上限丢弃未结束任务、验证依据或仍适用的决定。
2. 按结束年份将旧记录追加到 `docs/plans/archive-YYYY.md`，保留编号、日期、目标与范围、最终状态、关键决定、结果、验证依据及后续链接。可删除重复过程文字；一行摘要不能成为唯一留存记录。原记录缺少日期或依据时保留未知，先核实，不能编造。
3. 先核对归档内容和链接，再移除主文件中的对应条目。已有归档按编号去重；编号相同但内容不同时先核对差异，不能覆盖或丢弃其中一版。相对链接按新的文件位置修正。
4. 主文件只保留每年一个归档链接，避免逐条摘要形成第二份无限增长的历史。长篇活动计划可放到 `docs/plans/<计划编号>.md`，当前计划仍保留状态、范围、验收、下一步和详情链接。
5. 更新相关导航及上下文中的实际结构树，检查引用后重新运行 `--check`。如果内容仍超限，如实报告；不要自行提高或关闭用户的上限以消除问题。

这里的归档是 Agent 维护动作。脚本只报告体积，不会移动、压缩或删除条目。

## 审阅另外两份文档

- **上下文准确性：** 对照依赖清单、入口代码、配置、目录和已确认的决定核实对应段落。尚未创建的路径及未落实方案放回计划；已有事实过时就修订，不追加互相矛盾的历史段落。
- **整理日期：** 实际核实内容后才更新 `最后整理：YYYY-MM-DD` 或 `Last reviewed: YYYY-MM-DD`；日期新不证明内容正确。没有变化也可记录真实复核日期，不能只改日期让检查通过。
- **README 可用性：** 安装、启动说明应包含所需环境、执行目录、无凭据配置示例和预期结果；适用时验证命令，未实现或未验证的用法明确标注。确认导航指向存在的文档，lite 升级后补齐入口并移除过时的“小项目模式”说明。
- **长度与重复：** 上下文保持可快速理解项目，README 保持可快速开始使用。长篇设计、操作手册和历史移到合适位置并链接；不为了只保留三个 Markdown 文件而把所有细节塞回入口，也不把当前有效事实当历史归档掉。

## 检查能力的边界

以下是 `standard` 的自动检查范围；`basic` 跳过内容检查，`strict` 额外要求完整文档、可解析结构树、已有提交和干净工作区。

| 文档 | 自动检查 | 仍需内容审阅 |
| --- | --- | --- |
| `PLANS.md` | 可读、非空、指定占位符、默认 16 KB 体积上限 | 状态是否真实、验收证据是否充分、未结束任务是否保留、历史是否超过 5 条、归档和链接是否完整 |
| `PROJECT_CONTEXT.md` | 可读、非空、指定占位符、整理日期可解析且不在未来、默认 30 天时效、结构树与实际顶层名称差异 | 稳定事实准确性、细节目录、长期决定依据、长度和重复内容 |
| `README.md` | 可读、非空、指定占位符 | 运行命令有效性、说明是否过期、文档入口与链接、长度和重复内容 |

结构树缺失在 standard 下是警告，在 strict 下阻止通过。顶层比较忽略隐藏项，常见依赖与构建目录允许省略；它不核实文件职责或任意深度目录。

README 和上下文目前没有硬性体积限制，也不做全文相似度或链接检查。报告检查结果时区分脚本发现和内容审阅发现；`result: healthy` 不能表述为所有文档约定已满足。

既有文件由生成器保留，不会自动获得新版约定。用户授权改进文档时进行定点合并，保留原内容和有效的项目特定规则；只读审阅时只报告问题。
